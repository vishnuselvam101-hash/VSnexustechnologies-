## 1. What "V0.1" actually is

* The repository history is `49defd3` (initial commit, README only) followed by 5 commits from branch
  `codex/build-vnx-dna-rd-1-application`, merged as `cf7d1f5`. There were no tags before this baseline.
* **Version labels disagree.** `pyproject.toml` and `vnxdna.__version__` say `1.0.0`. `vnxdna.config.VERSION`
  says `0.1.0`. The README calls the system "VNX-DNA-1" and the API calls it "R&D-1". This project treats
  the code as the **V0.1 research prototype**. The `1.0.0` label is not supported by the evidence below.
* The repository contains **two independent pipelines**:

| Pipeline | Modules | Container | Used by |
|---|---|---|---|

## 2. Architecture as implemented (dataset pipeline)

`encode_file`: read the whole file → compress (`none`/`zlib` level 6/`zstandard`) → optional Fernet
encryption → then either

* **ecc=none**: fixed-size payload strands (`VNX1|dataset_id|index|total|len|sha256` FASTA header), or
* **ecc=reed_solomon**: stripes of K data shards plus M parity shards (`VNX2|dataset_id|stripe|shard|K|M|len|sha256`), with the last stripe zero-padded.

Each payload is mapped to DNA using `baseline_binary_2bit` (4 nt/byte) or `constrained_v1` (8-nt codebook
words, 1 bit/nt, 50% GC). The pipeline then runs constraint validation and writes a JSON manifest (`format_version`: 1 = no ECC,
2 = RS, 3 = constrained).

`decode_dataset`: parse the manifest and FASTA → group strands by index/stripe → run per-strand constraint
checks, decoding, and length/SHA-256 checks. On the RS path, invalid shards become erasures and are solved
by Gaussian elimination. After that, the pipeline decrypts, decompresses, and checks the final SHA-256 against the manifest.
Output is written only after that final check.

| Layer (target) | V0.1 state |
|---|---|
| Compression | zlib/zstd/none. Unbounded decompression. |
| Encryption | Fernet (AES-128-CBC + HMAC-SHA256), an established AEAD-style construction. Key comes from `VNXDNA_KEY` or `--encryption-key`. |
| Chunking | Fixed-size. Whole input is held in memory. |
| Metadata | JSON manifest with a `format_version` integer. There is no schema document, and the manifest is not authenticated. |
| Integrity | Per-strand SHA-256 (hash in FASTA header) and final SHA-256 of the plaintext. |
| Erasure coding | Systematic GF(256) "Vandermonde" shard codec. **Not MDS**, see §4.1. |
| Error correction (substitution) | None at nucleotide level. A substitution invalidates the shard checksum, and the shard becomes an erasure. |
| Indel handling | None. Detected only as a checksum or length failure, which becomes an erasure. |
| DNA encoding | 2-bit baseline, plus `constrained_v1` codebook. |
| Constraint model | GC range, homopolymer, motifs, min/max length. Validation only. |
| Channel simulator | Substitution, insertion, deletion, dropout, duplicate, reorder. Seeded. |
| Addressing | **Out-of-band.** Index, dataset ID, and checksum live in ASCII FASTA headers, not in the DNA sequence. The simulator never corrupts headers. See §4.4. |
| Random access | None in the dataset pipeline. The legacy archive offers per-file lookup inside one JSON file. |
| CLI | typer: `encode decode inspect simulate verify benchmark info` |
| API | FastAPI, loopback-only by Dockerfile convention, no authentication |
| Benchmarks | `vnx-dna benchmark` (one run, one config), plus legacy E001–E008 |

## 4. Defects and risks found by probing

Every item below was reproduced with `research/v0_1_forensics/`. Severity reflects the correctness of documented claims.

### 4.1 CRITICAL: the Reed–Solomon shard codec is not MDS

The generator is `[I_K ; V]`, where `V[p][c] = (p+1)^c` over GF(256). An identity matrix stacked on raw
Vandermonde rows does not guarantee that every K×K submatrix is invertible. The docs and README promise
"up to M erasures per stripe". Measured results:

| K,M | patterns tested | unrecoverable patterns with ≤ M erasures |
|---|---|---|
| 4,2 | 15 (all) | 0 |
| **8,4 (README default)** | 495 (all) | **10** (e.g. erase shards {4,5,7,11}) |
| 10,4 | 1001 (all) | 20 |
| 16,4 | 4845 (all) | 72 |
| 16,8 / 20,10 / 32,8 / 32,16 / 64,16 / 64,64 | 3000 sampled each | 83 / 51 / 56 / 69 / 31 / 23 |

Failure is **safe**: decoding raises `ECCRecoveryError: ... not linearly independent`, and no corrupt output
is written. The stated erasure capability is still false for most configurations. `recover()` also
tries only the first K available shards and never tries another subset. The fix requires a new generator,
such as a Cauchy matrix or `V·V_top⁻¹`, and therefore a new format version. Existing format-2/3 datasets must
stay decodable with the old matrix.

### 4.2 HIGH: `vnx-dna simulate` never works

The CLI command function is named `simulate`, which shadows the imported `simulation.channel.simulate`. It calls
itself and fails with `maximum recursion depth exceeded`. No test covers the CLI.

### 4.3 HIGH: committed experiment results are not trustworthy

* `results/raw/E00*.json` record `git_commit 49defd3` (the README-only initial commit) and Python 3.14.4.
  The code that produced them is not the committed code at that SHA.
* E004 reports "success" for 0–20% dropout. Re-running shows the input yields 3 chunks, and the fixed seed
  drops **0 chunks in every case**. The result says nothing about dropout tolerance.
* E003's `mixed` case failed because of a harness bug (`simulate_errors() got an unexpected keyword argument
  'mixed_rate'`), and it is recorded as an experimental failure.
* All experiments use one trial, and they run the **legacy** pipeline, not the dataset pipeline that the CLI ships.
* `.gitignore` lists `results/raw/*.json` and `results/processed/*.csv`, yet these files are tracked.

### 4.4 HIGH (architectural): addressing and checksums are not stored in DNA

Strand index, dataset ID, K/M, length, and SHA-256 live in ASCII FASTA headers. The channel simulator mutates only
the sequence, so every recovery result so far assumes a perfect, error-free index channel. A physical
system has to carry addresses inside the molecule, where they suffer the same errors. Every recovery rate reported so
far is therefore optimistic by construction.

### 4.5 MEDIUM: duplicate observations are not exploited

V1 and V2 both keep only the **first** observation of an index. If the first copy is corrupt and a later
copy is valid, decoding fails (V1 `IntegrityError`; V2 counts an erasure and can exceed capacity). In V1, a
foreign-dataset strand with a colliding index shadows the valid strand (`MetadataError`), while V2 filters it out correctly.

### 4.6 MEDIUM: malformed manifests raise untyped exceptions

A missing `config.constraints` raises `KeyError`. An unknown config key, a non-integer `strand_count`, or a non-dict `config` raises
`TypeError`. These escape the `VNXDNAError` hierarchy. They are not silent corruption, but they are not
clean failures either. There is no manifest schema.

### 4.7 MEDIUM: encryption leaks metadata; the manifest is unauthenticated

With encryption on, the manifest still holds the plaintext `original_name`, `original_size`, and
**`original_sha256` of the plaintext**. That hash confirms guesses of low-entropy content (probe: `sha256(b"yes")`
matched). The manifest is not covered by the Fernet MAC. Tampering is caught only indirectly, through the final hash,
and the hash itself can be rewritten together with the data. Keys can be passed as `--encryption-key` on the command
line, where they are visible in the process list. Wrong-key handling is correct: `Authenticated decryption failed.`

### 4.8 MEDIUM: CLI exit codes and output

* Every error exits with code **2** (typer `BadParameter`, the usage-error code). The CLI does not distinguish
  ERROR, UNRECOVERABLE, and VERIFY_FAILED. `verify` is the exception: it exits 1 on failure.
* `verify` prints `RECOVERED SHA-256:` using the **manifest** value, not a recomputed hash. The equality
  check does happen inside `decode_dataset`, but the displayed number is not an independent measurement.

### 4.9 LOW: other findings

* Encoding is not reproducible. `dataset_id` (uuid4) and `created_at` appear in the manifest and every header,
  so identical inputs produce different `strands.fasta` files. The DNA payload sequences themselves are deterministic without encryption.
* The default strand is 2048 nt (512 B × 4 nt/B), far longer than typical synthesized oligos (~100–300 nt).
  This is valid in software, but it is not a realistic physical default.
* `decompress` is unbounded (decompression bomb). `SECURITY.md` acknowledges this.
* The pure-Python GF(256) arithmetic is slow (see §5).
* The two pipelines duplicate helpers: `codec/constraints.py` vs `validation/dna.py`, and `compression/codecs.py` vs `archive/archive.py`.

## 5. Baseline performance (single run, random input, `compression='none'`)

Source: `research/v0_1_forensics/baseline_perf.json`. These are single runs, so they are indicative only and have no variance estimate.

| Config | Size | Encode s | Decode s | Strands | nt/byte |
|---|---|---|---|---|---|
| baseline 2-bit, no ECC | 1 MB | 1.18 | 1.81 | 1954 | 4.00 |
| RS 8+4, 2-bit | 1 MB | 3.73 | 3.77 | 2940 | 6.02 |
| RS 8+4, constrained_v1, 256 B strands | 1 MB | 5.59 | 3.62 | 5868 | 12.02 |

These give ≈0.85 MB/s encode without ECC and ≈0.27 MB/s with RS. 10 MB was not measured at baseline. Linear
extrapolation gives about 40 s per direction for RS, but that figure is unmeasured. Small inputs have high relative overhead
because the last stripe is zero-padded (1 kB → 24.6 nt/byte with RS 8+4).

## 6. What V0.1 does correctly (verified)

* Error-free round trip for empty, 1-byte, random, and UTF-8 inputs in all three formats.
* Output is written only after the final SHA-256 check passes. No silent corruption was observed in any probe.
* Checksum-detected substitutions and indels become erasures. Recovery works within capacity for K=4, M=2.
* Wrong Fernet key and modified ciphertext are rejected.
* Reordering and duplicates are handled, apart from the first-copy issue in §4.5.
* `constrained_v1` round trips, and every word has 50% GC and bounded homopolymers.
* Unsupported `format_version` values are rejected.

## 7. Implications for V0.2

In priority order:

1. Replace the RS generator with a provably MDS construction in a new format version. Keep a legacy
   decoder for formats 2/3, and add exhaustive erasure-pattern tests.
2. Fix the CLI `simulate` recursion. Add CLI tests and meaningful exit codes.
3. Define a versioned, schema-validated, authenticated container. Remove plaintext hash leakage when encrypted,
   and make encoding deterministic given a seed or dataset ID.
4. Decide the future of the legacy archive pipeline, then quarantine or retire it along with E001–E008. Regenerate any kept
   results from the shipped pipeline with recorded provenance.
5. Move addressing into the DNA (in-band index plus its own protection). Model header or index errors in the channel.
